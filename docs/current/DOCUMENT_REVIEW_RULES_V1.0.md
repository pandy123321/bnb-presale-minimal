# 文档审核规则 V1.0

状态：`ACTIVE`  
适用对象：产品、架构、数据库、API、事件、状态机、合约修复计划、部署计划、审计报告、测试计划、阶段证据、冻结/发布 Gate 文档。  
审核模式：默认只读。除非任务明确授权，审核 Agent 不得修改任何文件、运行测试、构建、Migration、RPC、Fork、部署、签名、广播或链上交易。

## 1. 目标与基本原则

文档审核的目标不是润色文字，而是判断文档是否：

1. 真实反映可验证的代码、合约、部署证据或已批准决策；
2. 在自身范围内完整、自洽、可执行且可审计；
3. 不把计划、假设、静态设计、测试结论、运行时事实和发布批准混为一谈；
4. 不通过模糊表述、缺失输入、越权授权或未闭合责任边界绕过安全 Gate；
5. 能让下一位实现者、审核者和责任人得到同一份明确、可复现的约束。

证据优先级从高到低如下：

1. 已部署链上合约字节码、固定区块 readback、交易回执和不可变链上事实；
2. 经确认的部署源 Commit、ABI、构建产物和部署台账；
3. 当前仓库中可定位的代码、SQL、OpenAPI、Event/State 机器规范；
4. 已签署的责任人决策、审计结论和阶段证据；
5. 产品/架构/计划文档；
6. 口头说明、历史报告摘要或未经验证的外部材料。

较低优先级内容不得覆盖较高优先级事实。出现冲突时，必须明确冲突、引用双方证据，并要求责任人决策；不得自行臆测。

## 2. 审核边界

每次审核开始前，审核 Agent 必须明确：

- 审核范围：目录、文件、版本、Commit、附件和排除项；
- 审核类型：计划审核、实现前冻结审核、变更复审、代码/文档一致性审核、发布前文档 Gate；
- 允许的验证动作：例如只读搜索、结构解析、交叉引用检查、静态 SQL/OpenAPI/YAML 检查；
- 明确未执行的动作：测试、构建、数据库执行、RPC、部署、签名、链上操作等；
- 当前工作树或上传包是否完整，是否能够验证每项结论。

除非用户明确授权，审核 Agent 不得：

- 修改代码、合约、SQL、OpenAPI、部署配置或测试；
- 运行会写入数据库、链、缓存、文件或外部系统的命令；
- 下载依赖、访问未授权网络资源或将私密材料传出；
- 将“文档通过”表述为“代码通过”“测试通过”“已部署”“可上主网”。

## 3. 上传与附件完整性规则

审核 Agent 必须先输出“材料完整性矩阵”，再给出结论。

### 3.1 必需材料

按任务范围收集以下材料；不存在或不适用时必须明确写出原因：

- 待审核文档的完整目录，而不是只截取摘要；
- 文档直接引用的 SQL、OpenAPI、Event Catalog、State Machine、接口或配置；
- 被声明为权威来源的产品文档、规则原文、合约基线、部署基线、审计报告；
- 与本轮 Finding 直接相关的历史审核结论和修订记录；
- 需要验证“与代码一致”时，对应源码或固定源码快照；
- 提供文件完整性清单时，清单本身、SHA-256 和文件大小。

### 3.2 缺失材料的处理

- 缺少某个文件，只影响依赖该文件的结论；其他可独立验证项继续审核。
- 对无法验证的项目使用 `UNABLE_TO_VERIFY` 或 `BLOCKED`，不得推测为 PASS。
- `BLOCKED` 不等于发现漏洞；必须说明是“材料不足”“工具限制”“外部状态不可达”还是“需要责任人决策”。
- 不得因上传包缺少根目录规则原文，就否定已经由 SQL/OpenAPI/代码直接验证的技术事实。
- 不得把“文件名编码异常”当作内容损坏；应以文件内容、大小和 hash 为准。

## 4. 文档真实性与一致性审核

审核 Agent 必须逐项检查以下关系。

### 4.1 权威性和版本

- 文档是否标注状态、日期、适用范围、版本或 Commit；
- 是否明确“已部署事实”“当前代码事实”“计划候选”“待验证 Gate”的边界；
- 是否错误使用 public branch、旧部署地址或过时文档替代目标快照；
- 是否存在两份互相冲突且未标记失效的基线；
- 历史报告是否被明确标为历史记录，避免旧计数/旧状态被当作当前结论。

### 4.2 交叉文档一致性

至少检查：

- 产品能力表与 API、数据库、合约事实源是否一致；
- 架构职责与 SQL Role/Grant 是否一致；
- API 文档、DTO、状态机、错误码和异步命令语义是否一致；
- Event Catalog、ABI、部署地址、起始区块和状态机是否一致；
- 数据库表、外键、唯一键、Trigger、View 与权限脚本是否一致；
- 阶段计划、依赖关系、Build Gate、审核 Gate、证据模板是否一致；
- 品牌名称、链上 Token/ABI 名称、网络、地址来源、Mainnet 禁令是否一致；
- README、Self Review、目录索引、对象数量、路径/operation 计数和角色摘要是否与机器规范一致。

### 4.3 机器规范优先检查

当文档声称某项可执行时，优先核对机器规范：

- SQL：表、列、CHECK、FK、UNIQUE、INDEX、FUNCTION、TRIGGER、GRANT、REVOKE；
- OpenAPI：路径、operationId、requestBody 是否 required、schema 是否 closed、`$ref` 是否可解析；
- YAML：是否可解析、状态转换目标是否存在、终态是否仍有出边、事件流是否完整；
- 权限：每个角色的读写对象和列是否满足职责最小化；
- 代码：调用链、实际写入者、错误路径、幂等键、并发约束和终态保护。

仅有 Markdown 声明、没有机器规范或代码证据时，只能写“计划已声明”，不得写“已实现”或“已关闭”。

## 5. 安全与业务逻辑审核规则

涉及资金、权限、合约、治理、签名、分红、快照、预言机或异步命令时，必须额外检查。

### 5.1 权限与职责闭环

对每个运行角色列出：

- 必需读取什么；
- 必需写入什么；
- 不应获得什么权限；
- 是否有完整、可执行的业务闭环；
- 是否存在“无法完成职责，迫使实现者扩大权限或绕过 Gate”的死路。

重点检查：

- 整表 `UPDATE/DELETE` 是否应收窄为列级权限；
- 不可变身份、审批、审计、Artifact、Preflight、Command 是否同时有 GRANT 和 Trigger 保护；
- 创建者、审批者、签名者、执行者、审核者是否职责分离；
- 签名者是否能创建、篡改、续期或复活待签名 Command；
- 事件派生状态是否存在唯一权威写入者；
- 运行角色是否有机会绕过不可变证据、审批或发布 Gate。

### 5.2 数据与状态安全

至少检查：

- 状态初态、合法转移、终态、失败重试、取消和恢复是否一致；
- 首次失败、重复执行、并发请求、超时、重组、过期和回滚是否有明确语义；
- 幂等键是否覆盖所有影响结果的输入；
- 同一不可变证据是否只能被单次消费；
- 过期对象是否能安全重建新 revision，且旧记录不被复用或原地修改；
- 快照是否绑定 block number/hash、canonical/finalized 条件与固定输入；
- Artifact、Allocation、Approval、Preflight、Command、链上事件之间是否精确绑定 hash/root/amount/version；
- current projection 是否能污染历史快照；
- checksum 的输入字段、排序、编码、NULL、换行、哈希算法与大小写是否冻结。

### 5.3 文档中禁止的危险表达

发现以下表达必须至少标记 P1 或要求澄清：

- “自动部署”“可直接主网”“无需复核”“默认成功”；
- “可按实现者自行决定”“必要时临时扩大权限”“先绕过再补”；
- 未指定来源的地址、ABI、RPC、角色、金额、税率、区块或参数；
- 将 `NOT_RUN`、静态检查、计划完成、人工估计写为 `PASS`；
- 将测试网地址、主网地址、旧部署地址或未验证地址混用；
- 把用户批准、独立审核、责任人签字伪装为技术自动条件。

## 6. Finding 分级规则

每条 Finding 必须有可定位证据和可达场景；不以猜测或泛泛建议作为阻断项。

| 等级 | 定义 | 默认处理 |
|---|---|---|
| P0 | 可导致资金损失、权限绕过、秘密泄露、错误链/环境写入、不可逆破坏或主网错误授权 | 立即阻断；不得进入下一阶段 |
| P1 | 核心流程不可执行、状态/权限闭环缺失、可重放/并发/篡改、错误成功、错误冻结或明确安全 Gate 可绕过 | 修复并独立复验后才能关闭对应 Gate |
| P2 | 非阻断但会造成歧义、fail-closed 死锁、文档漂移、可维护性/可审计性下降或后续实现高风险 | 纳入修订计划；是否阻断由明确 Gate 决定 |
| P3 | 信息性建议、命名、格式、可读性或低风险优化 | 记录即可，不得虚增为阻断项 |

每条 Finding 必须包含：

1. 编号和等级；
2. 文件路径与精确行号、章节或 SQL/API 对象；
3. 当前证据；
4. 触发条件与可达场景；
5. 技术/资金/业务影响；
6. 最小安全修正建议；
7. 是否阻断哪个 Gate；
8. 是否需要源码、运行时验证或责任人决策。

## 7. 结论与 Gate 规则

审核结论必须使用以下之一，并说明适用层级：

- `APPROVED_FOR_DESIGN_GATE`：仅允许指定的文档/设计阶段开始；不等于允许编码、合约修改、测试网部署或主网部署。
- `APPROVED_FOR_RESPONSIBLE_OWNER_FREEZE`：静态设计已通过独立审核，可进入责任人签署；不等于运行时或发布通过。
- `CHANGES_REQUIRED`：存在未关闭 P0/P1，或指定 Gate 的关键输入不完整。
- `BLOCKED`：无法进行所需验证，且缺失材料/外部状态直接影响该 Gate 判断。
- `UNABLE_TO_VERIFY`：某一事实无法独立证明；必须说明缺少什么。

任何结论都必须同时声明：

```text
DOCUMENT_REVIEW_RESULT = ...
CODE_IMPLEMENTATION_APPROVAL = YES / NO / NOT_IN_SCOPE
TEST_APPROVAL = YES / NO / NOT_IN_SCOPE
DEPLOYMENT_APPROVAL = YES / NO
TESTNET_REDEPLOY = ALLOWED / FORBIDDEN / NOT_IN_SCOPE
MAINNET = NO-GO / NOT_IN_SCOPE / APPROVED_BY_SEPARATE_GATE
```

除非任务明确要求并完成独立发布审查，文档审核默认：

```text
DEPLOYMENT_APPROVAL = NO
MAINNET = NO-GO
```

## 8. 修订与复验规则

当用户授权修复文档时，修订 Agent 必须：

1. 先判断外部 Finding 是否正确；
2. 只修改被证实有问题的文档、机器规范或冻结契约；
3. 不把历史审核报告改写成“从未发生”，应新增修订记录并标注其历史状态；
4. 同步更新目录索引、自审、对象计数、角色摘要、状态和下一轮审核提示词；
5. 对每个 P1 明确写 `FIX_READY / INDEPENDENT_RETEST_PENDING`，不得由修订者自行关闭；
6. 完成只读自审，检查交叉引用、对象存在性、旧规则残留和权限回归；
7. 输出下一轮独立审核需要的完整上传清单。

修订后只有独立审核 Agent 才能将 Finding 标为 `CLOSED`。作者自审、实现者自审和同一会话内重复确认不能替代独立复验。

## 9. 审核输出模板

审核 Agent 必须按以下结构输出。

```markdown

## 1. 审核结论

```text
DOCUMENT_REVIEW_RESULT = APPROVED_FOR_DESIGN_GATE / APPROVED_FOR_RESPONSIBLE_OWNER_FREEZE / CHANGES_REQUIRED / BLOCKED
P0 = <数量>
P1 = <数量>
P2 = <数量>
P3 = <数量>
CODE_IMPLEMENTATION_APPROVAL = YES / NO / NOT_IN_SCOPE
DEPLOYMENT_APPROVAL = NO
MAINNET = NO-GO

## 10. 审核 Agent 行为约束

- 审核真实文件，不只相信提交说明、报告摘要或自审结论；
- 结论必须贴近证据；无证据时写 `UNABLE_TO_VERIFY`；
- 不得把未运行的测试、未执行的 Migration、未读取的 RPC、未签署的责任人批准报告为 PASS；
- 不得把缺少测试自动报告为“本轮文档 Bug”，除非文档虚假声称测试已通过；
- 不得扩大审核范围到用户明确排除的代码、环境或部署；
- 不得因发现 P2/P3 就推翻已证实的 P0/P1 关闭结论；
- 不得为追求“无问题”而重复提出没有新证据的新验收条件；
- 不得泄露 `.env`、私钥、助记词、API Key、带凭据的 RPC URL 或内部敏感资料；
- 不得以任何形式授权主网、广播、签名或重部署，除非用户另行给出明确权限并完成独立发布 Gate。

## 11. 版本维护

本规则的变更必须记录：变更日期、版本、变更原因、影响的审核模板和是否需要重新审核既有结论。规则本身不覆盖项目的专用合约安全规范、开源准入规则或项目审批流程；发生冲突时，遵循更严格的一方。
